## 0. 이 문서를 어떻게 쓰나

이 문서는 **"완성된 코드를 설명하는 문서"가 아니라 "만들어가는 동안 무엇이 어긋났고 어떻게 알아챘는지의 기록"** 입니다.

교육 내용 4단계 중 **3단계(생성형 AI 활용)** 는 코드를 잘 뽑아내는 능력이 아니라 **AI가 만든 결과가 틀렸는지 알아채는 능력**입니다. 그래서 이 문서의 절반은 §6 "실제로 잡힌 오류"에 할애했습니다. 거기가 수업의 핵심입니다.

## 1. 무엇을 만들었나

공주 지역 관광지를 **사용자 취향에 맞춰 추천하고, 하루 코스를 짜주는 웹 서비스**입니다.

### 완성본 규모

| 항목 | 수치 |
|---|---|
| 코드 | `src/` 8개 모듈 **1,037줄** |
| 테스트 | 인수 13개 + 골든 21개 = **34개** |
| 데이터 | 관광지 **237건** (공주 103건 / 관광지 136·음식점 82·문화시설 19) |
| 가상 사용자 | **50명**, 방문이력 701건 |
| 커밋 | 4개 |

### 화면 구성

```
① 나와 비슷한 사람이 좋아한 곳     ← 협업 필터링
② 이 곳과 비슷한 곳 찾기            ← 콘텐츠 기반 추천
③ 오늘의 여행 코스                  ← 오전-점심-오후-저녁 + 경로 지도
```

### 기술 선택과 그 이유

| 레이어 | 선택 | 이유 |
|---|---|---|
| 언어 | Python 3.11+ | 학생이 배울 언어를 하나로 |
| 웹 | **Streamlit** | 파일 하나가 곧 앱. HTML/CSS/JS 없이 화면을 만든다 |
| 추천 | pandas + scikit-learn | 표준 라이브러리만. 직접 만든 프레임워크 없음 |
| 데이터 | TourAPI (공공데이터포털) | 실제 관광 데이터 |
| 배포 | Streamlit Community Cloud | 무료, GitHub 연결만으로 공개 URL |

> **왜 React를 안 썼나**: 화면과 서버를 나누면 파일이 20개로 늘고 그 사이를 오가는 코드가 생깁니다. 3일 수업에서 그 비용을 감당할 수 없습니다. Streamlit은 파이썬만 알면 화면이 나옵니다.
>
> **왜 Vercel에 배포하지 않았나**: Vercel은 요청이 올 때만 잠깐 실행되는 방식입니다. Streamlit은 계속 켜져 있는 서버가 필요해서 구조적으로 맞지 않습니다. 배포지를 정할 때는 **"내 앱이 어떤 방식으로 실행되는지"** 를 먼저 봐야 합니다.

## 2. 기획 — "만들었다"를 기계가 판정하게 만들기

### 문제

"추천 서비스를 만들자"는 목표는 **완성 여부를 판단할 수 없습니다.** 화면이 뜨면 완성인가? 추천이 나오면 완성인가? 그 추천이 엉터리라면?

특히 추천 시스템은 **에러 없이 잘못되는** 대표적인 분야입니다. 코드가 멀쩡히 돌아가는데 모든 사람에게 같은 곳을 추천하거나, 유사도가 전부 똑같이 나오거나, 이미 가본 곳을 또 추천할 수 있습니다. **눈으로는 못 잡습니다.**

### 해결 — 교육 내용 4단계를 8개 기능으로 쪼개고, 각각에 숫자 기준을 붙였다

| ID | 교육 단계 | 기능 | 판정 기준 | 판정 방식 |
|---|---|---|---|---|
| F1 | 1단계 | 관광지 수집 | 150건 이상, 필수컬럼 결측 0 | **자동** |
| F2 | 1단계 | 사용자·방문이력 | 50명 이상, 행렬 밀도 3~15% | **자동** |
| F3 | 2단계 | 콘텐츠 기반 추천 | Top-5, 자기 자신 제외, 유사도 분산>0 | **자동** |
| F4 | 2단계 | 협업 필터링 | Top-5, 방문지 제외, 콜드스타트 처리 | **자동** |
| F5 | 2단계 | 코스 생성 | 4슬롯, 총 이동거리 60km 이하 | **자동** |
| F6 | 4단계 | 웹앱 | 에러 없이 기동, 3초 내 렌더 | 반자동 |
| F7 | 4단계 | 배포 | 공개 URL 접속 가능 | 수동 |
| F8 | 3단계 | AI 협업 기록 | 프롬프트→코드→오류수정 10턴 이상 | 수동 |

**F1~F5는 `pytest` 한 번으로 판정됩니다.** "다 됐어요"라는 말 대신 숫자가 답합니다.

```bash
python -m pytest tests/ -q
```

### 여기서 배울 것

기준을 **미리, 숫자로** 정해두면 세 가지가 생깁니다.

1. **판정이 다툼거리가 안 됩니다.** 밀도 3~15%는 해석의 여지가 없습니다.
2. **AI에게 목표를 줄 수 있습니다.** "좋은 추천을 만들어줘"보다 "유사도 분산이 0보다 커야 해"가 훨씬 잘 작동합니다.
3. **자기 기만을 막습니다.** 기준을 나중에 정하면 만든 것에 맞춰 기준을 낮추게 됩니다.

> **주의**: 기준을 정직하게 지키는 것이 핵심입니다. §6-2에서 이 프로젝트가 실제로 **기준을 만족시켰지만 실제로는 나빠진** 사례를 다룹니다.

## 3. 개발 환경 설계 — 규칙을 말이 아니라 장치로

### 문제

AI에게 "API 키를 코드에 넣지 마"라고 말하면 **대부분** 지킵니다. 대부분입니다. 20명이 각자 AI를 쓰면 누군가는 키를 코드에 박아 GitHub에 올립니다.

### 해결 — 지켜야 할 규칙을 파일을 쓰는 순간 막는 장치로 내렸다

`.claude/hooks/` 에 파이썬 스크립트 3개를 두고, 파일을 쓰거나 고칠 때 자동 실행되게 했습니다.

| 장치 | 하는 일 |
|---|---|
| `guard_secrets.py` | 코드에 API 키가 들어가면 **쓰기 자체를 차단** |
| `regression_gate.py` | 되던 테스트가 깨지면 **다음 작업을 차단** |
| `session_brief.py` | 작업 시작할 때 현재 상태와 규칙을 다시 알려줌 |

### 회귀 게이트가 특히 중요한 이유

개발 초기에는 **모든 테스트가 실패합니다.** 당연합니다. 아직 안 만들었으니까요. 그래서 "전부 통과해야 진행"이라는 규칙을 걸면 첫 줄부터 막혀버립니다.

그래서 이 게이트는 **"한 번이라도 통과했던 테스트가 깨질 때만"** 막습니다.

```
코드 수정 → 테스트 자동 실행
  ├ 아직 안 만든 기능이 실패  → 통과 (개발 중이니까)
  └ 되던 게 깨짐              → 차단 (앞으로만 가고 뒤로는 못 감)
```

### 이 장치들도 처음엔 고장나 있었다

**실습 포인트입니다.** 만들어 놓은 안전장치가 실제로 작동하는지 확인해야 합니다.

키 차단 장치를 6가지 방식으로 시험해봤더니 **2가지가 뚫렸습니다.**

| 코드 형태 | 결과 |
|---|---|
| `serviceKey = "aBcD…=="` | 차단 |
| `params = {"serviceKey": "aBcD…=="}` | **통과 (구멍)** |
| `url = f"…?serviceKey=aBcD…=="` | **통과 (구멍)** |

하필 **우리 프로젝트에서 가장 나올 법한 두 형태**였습니다. TourAPI는 키를 딕셔너리로 넘기라고 안내하기 때문입니다. 정규식을 고쳐 8가지 경우를 전부 시험하고 막았습니다.

또 차단 메시지가 **글자가 깨져서** 전달되고 있었습니다. 한글 인코딩이 어긋나서입니다. 차단은 되는데 왜 차단됐는지 읽을 수 없으면, 스스로 고칠 수가 없습니다.

> **배울 것**: 안전장치를 만들었다고 안전해지지 않습니다. **일부러 뚫어보고 확인해야** 합니다.

## 4. 1단계 — 데이터 탐색·전처리

### 흐름

```
TourAPI 호출 → data/raw/ 캐시 저장 → 정제 → data/processed/*.parquet
```

### 수집

공공데이터포털의 **한국관광공사 국문 관광정보 서비스**를 씁니다.

| 항목 | 값 |
|---|---|
| 주소 | `apis.data.go.kr/B551011/KorService2` |
| 목록 조회 | `/areaBasedList2` |
| 상세 조회 | `/detailCommon2` |
| 지역 코드 | 충청남도 `34`, **공주시 `1`** |
| 콘텐츠 타입 | 관광지 `12`, 문화시설 `14`, 음식점 `39` |
| 하루 사용량 | 개발계정 1,000건 |

> **공주시 코드가 1이라는 것은 어떻게 알았나**: 추측하지 않고 `/areaCode2` 를 실제로 호출해서 확인했습니다. 기획서 어디에도 이 숫자가 없었습니다. **모르면 문서를 뒤지지 말고 API를 한 번 호출해 보는 게 빠릅니다.**

### 캐싱 — 수업 당일을 위한 보험

받아온 원본을 `data/raw/` 에 그대로 저장하고 **GitHub에 함께 올립니다.**

이유는 세 가지입니다.
- 수업 당일 TourAPI가 죽어도 실습이 가능합니다
- 학교 방화벽이 외부 API를 막아도 됩니다
- **배포 서버에 API 키를 넣지 않아도 됩니다**

마지막 항목이 실제로 중요했습니다. 배포된 앱은 키가 없지만 커밋된 캐시로 실데이터 237건을 그대로 씁니다.

### 정제에서 결정한 것

| 결정 | 이유 |
|---|---|
| 위경도·이름·카테고리 없는 행은 버림 | 추천에 쓸 수 없음 (F1 결측 0 기준) |
| 공주 반경 **30km** 로 자름 | §6-2 참조 |
| 이미지 주소를 `https` 로 변환 | 배포 화면이 https라 http 이미지는 브라우저가 차단 |

### 가상 사용자 만들기

실제 회원이 없으니 **50명을 지어냅니다.** 각자에게 1순위·2순위 취향과 연령대·성별을 주고, 취향에 맞는 곳을 더 많이 방문한 것으로 기록합니다.

**밀도**가 핵심 지표입니다. 50명 × 237곳 = 11,850칸 중 실제로 채워진 칸의 비율입니다.

- 너무 빽빽하면(50%) 현실과 다릅니다. 사람은 관광지 절반을 가보지 않습니다.
- 너무 성기면(0.5%) 추천할 근거가 없습니다.
- 그래서 **3~15%** 로 정했고, 현재 **6.8%** 입니다.

## 5. 2단계 — 알고리즘 설계

### 추천 방식 두 가지

| | 콘텐츠 기반 | 협업 필터링 |
|---|---|---|
| 질문 | "이 곳과 **비슷한** 곳은?" | "나와 **비슷한 사람**이 좋아한 곳은?" |
| 근거 | 장소의 성질 (카테고리·설명) | 다른 사람들의 방문 기록 |
| 강점 | 새 장소도 추천 가능 | 뜻밖의 발견 |
| 약점 | 비슷한 것만 계속 나옴 | 기록 없는 신규 사용자는 불가 |
| 파일 | `src/content_based.py` | `src/recommender.py` |

### 콘텐츠 기반 — 장소를 숫자로 바꾸기

```
[카테고리·지역·타입 원-핫]  +  [이름·설명 TF-IDF]  →  코사인 유사도
        50% 가중치                    50% 가중치
```

**두 덩어리를 각각 정규화한 뒤 합칩니다.** 안 그러면 숫자가 큰 쪽이 결과를 지배합니다.

실제 결과입니다.

```
공주 갑사 철당간  →  갑사 (0.750)
                     공주상신리 당간지주 (0.698)
                     마곡사 (0.563)
```

같은 절, 그리고 **같은 종류의 유물(당간지주)** 을 찾아냅니다.

### 협업 필터링 — 비슷한 사람 찾기

1. 사람 × 장소 평점표를 만듭니다. **안 가본 곳은 0이 아니라 빈칸입니다.** 0은 "싫어함"이라는 뜻이 되어버립니다.
2. 사람마다 평균을 빼서 **취향의 치우침**만 남깁니다. 후하게 주는 사람과 짜게 주는 사람을 같은 기준으로 비교하기 위해서입니다.
3. 사람끼리 코사인 유사도를 재고, 비슷한 사람들의 평가를 가중평균합니다.
4. **이미 가본 곳은 결과에서 뺍니다.**
5. 기록이 없는 신규 사용자는 **인기순으로 돌려줍니다.** 에러를 내면 안 됩니다.

### 코스 생성

```
오전(관광지) → 점심(음식점) → 오후(관광지) → 저녁(음식점)
```

- 시작점은 그 사람의 추천 순위를 따르되, **공주 안에 있는 후보를 먼저** 봅니다
- 다음 장소는 가까운 3곳 중 **그 사람 취향에 맞는 곳**을 고릅니다
- 이미 가본 곳은 제외합니다
- 총 이동거리가 60km를 넘으면 다른 시작점으로 다시 시도합니다
- 그래도 못 맞추면 **넘었다고 화면에 표시합니다.** 넘은 걸 숨기지 않습니다

거리는 **하버사인 공식**으로 계산합니다. 지구가 둥글기 때문에 위경도 차이를 그냥 빼면 안 됩니다.

## 6. 3단계 — 생성형 AI 활용: 실제로 잡힌 오류들

**이 장이 이 수업의 핵심입니다.**

아래는 전부 **실제로 일어난 일**입니다. 코드는 에러 없이 돌아갔고, 인수 테스트 13개는 전부 초록이었습니다. 그런데도 틀렸습니다.

AI에게 검증 전담 역할을 따로 맡겨(`rec-verifier`) 네 번 검사했고, 판정은 **FAIL → FAIL → FAIL → PASS** 였습니다.

---

### 6-1. `isin`이 순서를 지키지 않는다

**증상** — 코스의 출발지가 이상했습니다.

**확인** — 20명을 조사했더니 출발지가 추천 1순위인 경우가 **1명뿐**이었습니다. 나머지 19명은 20순위였습니다.

**원인**
```python
ranked = sights[sights["id"].isin(rec_ids)]   # rec_ids 순서가 사라진다
```
`isin`은 "포함되는가"만 봅니다. **원래 표의 순서로 되돌립니다.** 추천 순위를 넣었는데 결과는 데이터가 저장된 순서였습니다.

**왜 테스트가 못 잡았나** — F5는 "4슬롯이 있고 60km 이하"만 봅니다. 출발지가 1순위인지 20순위인지는 기준에 없습니다.

**고친 뒤** — 시드가 1순위인 경우 1/20 → **16/20**

> **배울 것**: 코드가 돌아간다고 의도대로 도는 게 아닙니다. 라이브러리 함수가 **순서를 보장하는지** 확인해야 합니다.

---

### 6-2. 기준은 만족시켰는데 실제로는 나빠졌다 ★

**증상** — 실데이터로 바꾸자 F2 밀도가 2.78%로 떨어져 기준(3~15%) 미달이었습니다.

**내가 한 것** — 가상 사용자의 방문 범위를 공주 30km로 좁혔습니다. 밀도가 6.84%로 올라 **기준을 통과했습니다.**

**검증에서 지적받은 것**
```
밀도 = 평점 수 ÷ (사용자 수 × 평점이 붙은 장소 수)
```
분모가 **"평점이 붙은 장소 수"** 입니다. 방문 범위를 좁히면 **분모가 같이 줄어서** 밀도가 자동으로 올라갑니다. 데이터가 촘촘해진 게 아니라 **자를 바꾼 것**이었습니다.

전체 카탈로그(1,092곳) 기준으로 다시 재면 **1.28%** 였습니다. 오히려 나빴습니다.

**진짜 문제** — 방문 범위는 30km인데 관광지 목록은 충남 전역이라 **두 범위가 어긋나 있었습니다.** 그래서 다른 증상들도 같이 생겼습니다.
- 협업 필터링이 추천할 수 있는 곳이 전체의 **18.8%** 뿐
- "공주만 보기"를 켜도 결과의 **46.3%가 공주 밖**
- 50명 중 **25명의 하루 코스에 공주가 한 곳도 없음** (9명은 아침을 천안에서 시작)

**고친 방법** — 관광지 목록도 공주 30km로 통일했습니다. 237곳.

| | 통일 전 | 통일 후 |
|---|---|---|
| 밀도 (테스트 기준) | 6.84% | 6.84% |
| **밀도 (전체 기준)** | **1.28%** | **5.92%** |
| CF 추천 가능 범위 | 18.8% | **86.5%** |
| 코스가 공주를 벗어남 | 25/50 | **5/50** |

> **배울 것**: **지표를 만족시키는 것과 좋아지는 것은 다릅니다.** 지표가 안 나올 때 "어떻게 하면 이 숫자를 올릴까"가 아니라 **"이 숫자가 왜 안 나오는가"** 를 먼저 물어야 합니다. 두 밀도 값이 서로 가까운지 보는 것이 정직함의 확인 방법이었습니다.

---

### 6-3. TF-IDF가 한국어에서 죽어 있었다

**증상** — 서로 다른 장소의 유사도가 **1.0(완전히 같음)** 으로 나오는 경우가 있었습니다.

**확인** — 1,092곳 중 **611곳(56%)** 의 텍스트 특징이 **전부 0**이었습니다.

**원인** — `TfidfVectorizer(max_features=400)`. 영어는 띄어쓰기로 단어가 갈리지만, **한국어 장소 이름은 띄어쓰기가 거의 없어 이름 하나가 통째로 단어 하나**가 됩니다. 어휘가 1,299개로 불어났고 400개로 자르니 절반 이상이 잘려나갔습니다.

텍스트 특징이 0이면 카테고리만으로 유사도가 정해집니다. 그래서 카테고리가 같은 서로 다른 장소가 1.0이 됐습니다.

**고친 방법** — 문자 2~3글자 단위로 자릅니다.
```python
TfidfVectorizer(analyzer="char_wb", ngram_range=(2, 3), min_df=2)
```
'갑사'와 '각원사'가 '사'를 공유하는 것을 잡아냅니다.

**결과** — 0벡터 611곳 → **0곳**, 유사도 1.0 중복 → **0%**

> **배울 것**: 라이브러리 기본값은 **영어 기준**입니다. 한국어에 그대로 쓰면 조용히 망가집니다.

---

### 6-4. 캐시보다 키를 먼저 봤다

**증상** — 없었습니다. **배포하기 직전에 발견했습니다.**

**원인**
```python
if key is None:
    합성 데이터 사용    # ← 실데이터 캐시가 있어도 여기로 온다
if 캐시 있음: 캐시 사용
```
배포 서버에는 키가 없습니다. 그대로 올렸으면 **공개 URL에서 가짜 데이터가 돌아갔을 것**입니다. 캐시를 커밋해 둔 의미가 사라집니다.

**고친 방법** — 순서를 뒤집었습니다. 캐시 → 키 → 합성.

> **배울 것**: **조건문의 순서가 곧 우선순위**입니다. 그리고 "내 컴퓨터에서 되는 것"과 "배포 환경에서 되는 것"은 다릅니다.

---

### 6-5. 내 컴퓨터에서만 되던 코드

**증상** — 배포하자마자 실패했습니다.
```
ModuleNotFoundError: No module named 'src'
```

**원인** — `streamlit run src/app.py` 로 실행하면 파이썬이 모듈을 찾는 첫 위치가 **`src/` 폴더**가 됩니다. 그러면 `from src.course import ...` 는 `src/src/course.py` 를 찾다가 실패합니다.

로컬에서는 `python -m streamlit` 으로 돌렸는데, 이 방식은 **현재 폴더를 검색 경로에 함께 넣어줍니다.** 그래서 같은 코드가 내 컴퓨터에서만 돌았습니다.

**고친 방법** — import 보다 먼저 프로젝트 루트를 검색 경로에 넣습니다.

> **배울 것**: **실행 방법이 다르면 결과도 다릅니다.** 배포 환경을 흉내 내어 미리 확인해야 합니다.

---

### 6-6. `st.map`은 선을 그리지 못한다

**증상** — 코스 지도에 점만 4개 찍히고 **경로가 안 보였습니다.**

**확인** — `st.map`의 인자 목록에 경로 관련 옵션이 아예 없습니다. 점만 찍는 기능입니다.

**고친 방법** — `pydeck`의 `PathLayer` 로 순서대로 선을 잇고 번호를 붙였습니다. pydeck은 Streamlit이 이미 깔아주므로 추가 설치가 없습니다.

> **배울 것**: 화면이 기대와 다르면 **그 함수가 원래 그걸 할 수 있는지** 부터 확인합니다.

---

### 6-7. 캐시가 데이터 변경을 몰랐다

**증상** — 데이터를 다시 만들어도 추천 결과가 그대로였습니다.

**원인** — 계산 결과를 `@lru_cache`로 저장해뒀는데, **파일이 바뀐 것을 알 방법이 없습니다.**

**고친 방법** — 캐시 열쇠에 **파일 수정 시각**을 넣었습니다. 파일이 바뀌면 열쇠가 바뀌어 다시 계산합니다.

**그런데 이 수정이 새 문제를 만들었습니다.** 파일이 아직 없을 때 수정 시각을 읽으려다 죽었습니다. GitHub에서 막 내려받은 상태가 정확히 그 상황입니다. 검증에서 잡혔습니다.

> **배울 것**: **고친 것이 새로 망가뜨릴 수 있습니다.** 그래서 고친 뒤에도 다시 검사합니다.

---

### 6-8. 인수 기준이 요구하지 않으면 검사되지 않는다

**증상** — 50명 중 **7명의 코스에 이미 가본 곳**이 들어 있었습니다.

**원인** — 협업 필터링은 방문지를 제대로 걸렀지만, **코스 생성은 그 사실을 몰랐습니다.**

**왜 테스트가 못 잡았나** — F5 기준에 "방문지 제외"가 **없습니다.** 4슬롯과 60km만 봅니다.

> **배울 것**: 테스트는 **적어둔 것만** 검사합니다. 통과했다는 말은 "적어둔 기준을 만족했다"이지 "옳다"가 아닙니다.

---

### 6-9. 요약 — 무엇이 무엇을 잡았나

| 도구 | 잡은 것 | 못 잡은 것 |
|---|---|---|
| 인수 테스트 13개 | 기준으로 적어둔 것 | 6-1 ~ 6-8 **전부** |

| 검증 전담 AI | 6-1, 6-2, 6-7, 6-8 | — |

| 눈으로 보기 | 6-6 | — |

**어느 하나로도 충분하지 않았습니다.**

골든셋도 처음엔 장식이었습니다. 시드가 하나뿐이라 일부러 코드를 망가뜨려도 통과했습니다. 시드를 4개로 늘리고 나서야 5가지 교란을 전부 잡았습니다. **안전장치도 시험해봐야 안전장치입니다.**

## 7. 4단계 — 웹 시연과 배포

### 배포 경로

```
로컬 개발 → git commit → GitHub → Streamlit Cloud → 공개 URL
```

배포 전 확인한 것입니다.

| 확인 | 결과 |
|---|---|
| `.env`(API 키)가 GitHub에 안 올라가는가 | 제외 확인 |

| 캐시로 키 없이 동작하는가 | GitHub에서 내려받아 확인 |

> **API 키는 절대 커밋하면 안 됩니다.** 한 번 올라가면 지워도 기록에 남습니다. `.gitignore` 에 `.env` 를 넣고, 커밋 전에 반드시 확인합니다.

### 배포 후 발견한 것

| 문제 | 원인 |
|---|---|
| `No module named 'src'` | §6-5 |
| 사용자 목록이 1~2명으로 줄어듦 | 연령·성별로 걸러내니 조합에 따라 후보가 없어짐 |
| 코스 경로가 안 보임 | §6-6 |

**배포는 개발의 끝이 아니라 새로운 검증 단계입니다.**

## 10. 용어집

| 용어 | 뜻 |
|---|---|
| **인수 기준** | "다 만들었다"의 정의. 숫자로 적어 다툼의 여지를 없앤 것 |
| **콘텐츠 기반 추천** | 장소의 성질이 비슷한 것을 추천 |
| **협업 필터링** | 나와 비슷한 사람이 좋아한 것을 추천 |
| **코사인 유사도** | 두 벡터가 이루는 각도로 재는 닮음 정도. 0~1 |
| **TF-IDF** | 글에서 그 글만의 특징적인 단어에 큰 점수를 주는 방법 |
| **원-핫 인코딩** | 카테고리를 0과 1의 나열로 바꾸는 것 |
| **밀도** | 사용자×장소 표에서 실제로 채워진 칸의 비율 |
| **콜드스타트** | 기록이 없는 신규 사용자에게 추천할 수 없는 문제 |
| **하버사인** | 둥근 지구 위 두 지점의 거리를 재는 공식 |
| **회귀(regression)** | 되던 기능이 다시 망가지는 것 |
| **골든셋** | "이 입력에는 이 결과가 나와야 한다"를 박아둔 기준선 |
| **캐시** | 한 번 받은 것을 저장해 두고 다시 쓰는 것 |
